# 8.2 — Cross-attention: the decoder asks, the encoder answers ⏱️ ~10 min · folds are optional extra

## The hook

Lesson 5.3 already gave you the fix, in a different room: when remembering is hard, **stop remembering and start looking**. Attention let a token inside one sentence read every other token in that same sentence.

Cross-attention is the same trick pointed across the gap. The decoder, mid-sentence, asks a question — *"I am about to write a noun; which source word am I translating?"* — and reads the encoder's states directly. The source never has to be memorized, because it never went away.

Notice there is no vector-size slider in attention mode. There is nothing to tune, because there is no budget to run out of: a 5-word source keeps 5 states, a 50-word source keeps 50. The memory scales with the input instead of being fixed at design time.

## Where the Q, K, and V come from

Attention in lesson 5.3 had one rule: a **query** is compared against **keys** to produce weights, and those weights mix the **values**. Cross-attention keeps the mechanism identical and changes only the addresses:

| | Query | Key & Value | Masked? |
|---|---|---|---|
| Encoder self-attention | source token | source tokens | no — the whole source is known |
| Decoder self-attention | generated token | generated tokens | yes — causal, no peeking ahead |
| **Cross-attention** | **generated token** | **encoder outputs** | no — the source is fully visible |

That third row is the entire architectural novelty of the encoder–decoder transformer. Everything else you already assembled in Module 6.

Two consequences fall out immediately:

- **The encoder runs once.** Its outputs are computed before decoding starts and reused at every step, so the keys and values for cross-attention are computed once per sentence, not once per generated token. For Whisper transcribing a 30-second clip, the audio encoder fires once and the decoder reads it thirty-odd times.
- **Cross-attention is not causal.** Output token 1 may legally read the *final* source word — which is exactly what French, German, or Japanese word order sometimes demands.

## Alignment you never asked for

The attention weights form an $m \times n$ matrix: for each output token, how much of each source token it read. Plot it and you get a rough word-alignment map, with a diagonal that bends wherever the languages reorder.

Nobody supervised that. The model was trained only on "produce the right French sentence"; alignment is an *instrumental* behavior that happened to lower the loss. It is also the reason cross-attention has stayed useful for debugging: when a translation model hallucinates a name, you can look at where it was reading, and the answer is often "nowhere in particular."

Treat those maps as evidence, not proof. Attention weights show what was *read*, not what was *used* — a head can attend to a token and then contribute almost nothing through its value vector. Alignment plots are a strong diagnostic hint and a weak explanation.

## Tiny example: cross-attention in nine lines

```python
import torch
import torch.nn as nn

MODEL_DIM, HEADS = 256, 8
cross_attention = nn.MultiheadAttention(MODEL_DIM, HEADS, batch_first=True)

memory = torch.randn(1, 8, MODEL_DIM)        # encoder outputs: 8 source tokens
decoder_states = torch.randn(1, 3, MODEL_DIM)  # 3 tokens generated so far
source_padding = torch.tensor([[False] * 6 + [True] * 2])  # last 2 source slots are <pad>

context, weights = cross_attention(
    query=decoder_states,      # what the decoder wants to know
    key=memory, value=memory,  # what the encoder can answer with
    key_padding_mask=source_padding,
)
print(context.shape, weights.shape)   # [1, 3, 256]  [1, 3, 8]
```

The `weights` tensor is the alignment map: three output positions, eight source positions, each row summing to 1. And note `key_padding_mask` — batching sentences of different lengths means padding, and padding must be masked out of the keys or your model will happily learn to attend to `<pad>` and transcribe silence as words. In `nn.TransformerDecoderLayer` this is the `memory` argument and its `memory_key_padding_mask`; same idea, fewer lines.

<details>
<summary>🤓 The actual math (optional)</summary>

For decoder states $H_{\text{dec}} \in \mathbb{R}^{m \times d}$ and encoder outputs $H_{\text{enc}} \in \mathbb{R}^{n \times d}$:

$$Q = H_{\text{dec}} W_Q, \qquad K = H_{\text{enc}} W_K, \qquad V = H_{\text{enc}} W_V$$
$$\text{CrossAttn} = \text{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}} + M\right) V$$

- $W_Q$ projects the decoder's question; $W_K$ and $W_V$ project the encoder's answer — the source is never squeezed into a single vector
- $QK^\top$ is $m \times n$, so cost grows with source length times target length, not source length squared
- $M$ here contains only $-\infty$ for padded source positions; unlike decoder self-attention, there is no causal triangle
- $\sqrt{d_k}$ is the same scaling from lesson 5.3, keeping the softmax out of its flat, gradient-free regions

Bahdanau-style RNN attention (2015) computed the weights with a small feed-forward scorer instead of a dot product, but the shape of the idea — read all encoder states, weighted per output step — is identical.

</details>

## Recap 📌

- Cross-attention gives the decoder direct, weighted access to every encoder state, replacing the fixed-size bottleneck with memory that scales with input length
- Queries come from the decoder, keys and values from the encoder, and no causal mask applies — but source padding must be masked
- Word alignment emerges as a by-product of minimizing translation loss; it is a useful diagnostic, not a guarantee of what the model used
