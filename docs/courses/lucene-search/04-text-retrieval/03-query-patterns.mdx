## Expand terms under an explicit rule

Run `FullTextLab patterns` after [lab setup](../advanced-labs.mdx). It builds
four real queries against the normal, lowercased body field:

```java
new PrefixQuery(new Term("body", "bicy"));
new FuzzyQuery(new Term("body", "bicyle"), 1);
new WildcardQuery(new Term("body", "*cycle"));
new RegexpQuery(new Term("body", "bi.*"));
```

Each returns A and B, never private C. They happen to agree on this corpus;
they do not have equivalent semantics. Prefix requires an initial sequence.
Fuzzy matching allows bounded edits. Wildcards use `*` for a sequence and `?`
for a character. Lucene regular expressions describe an automaton over terms,
not a Java regex running against an entire stored document.

These query objects do not apply your ordinary analyzer to the supplied term.
Normalize intentional literal input consistently. A raw uppercase prefix can miss
a lowercased dictionary, while analyzing regex metacharacters as ordinary prose
can destroy the pattern. Expose an explicit pattern mode instead of guessing
whether punctuation represents user syntax.

## Typo tolerance has boundaries

`FuzzyQuery` supports at most two edits in this implementation and normally allows
adjacent transpositions. The longer constructor exposes maximum edits, an exact
prefix length, maximum expansions, and transposition behavior. A longer required
prefix reduces work but prevents recovering a typo in that prefix. Short terms
also have scaled-distance constraints; "two edits" does not mean every tiny string
can match every other tiny string.

Fuzzy matching retrieves documents for spelling variants. A spell checker instead
proposes replacement words or queries, possibly requiring corpus frequency or a
dictionary. Lucene's suggest module includes spell-checking utilities such as
`DirectSpellChecker`; their outputs still need domain tests. Run `FullTextLab spell`
to suggest `bicycle` for `bicyle`. Its separate `public_terms` field contains only
public source text: spell suggestions must not leak a private vocabulary. This
fixed-public fixture is not a dynamic per-user dictionary. Neither fuzzy terms
nor spelling suggestions imply that `bike` means `bicycle`. That is a synonym
or embedding decision, not edit distance.

## Why ten returned hits may still be expensive

Multi-term queries find matching dictionary terms and rewrite them into an
executable representation. Rewrite methods differ: some combine or blend term
statistics, some assign constant scores, and some use bounded top-term expansions.
Inspect the pinned API rather than assuming all expansions behave like an OR
of equally scored terms. A top-ten collector does not cap the cost of discovering
those terms. Leading wildcards often remove a useful dictionary prefix.

Limit input size, permitted fields, fuzzy expansions, automaton determinization
work, and overall request time. A regex complexity limit is not a complete query
timeout. Cancellation, queue limits, and fallback behavior also belong in the
service. Return a clear validation error rather than silently replacing an
expensive request with a different, surprising query.

postings still matters. Automaton construction complexity and execution complexity

## Recap 🐾

1. Fuzzy edits, prefix matching, wildcards, and regex encode different term-level rules.
2. Programmatic patterns need deliberate normalization, syntax policy, and bounded expansion.
3. Small result limits do not guarantee cheap dictionary expansion or safe requests.
