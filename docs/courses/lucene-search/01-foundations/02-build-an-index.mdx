## Run the complete lab

Use **JDK 21 or newer and Maven 3.9+**. Check `java -version` and `mvn -version`;
Maven must also report a compatible Java runtime. Download these two course assets:

- <a href={useBaseUrl('/labs/lucene-search/pom.xml')} download>Maven project configuration</a>
- <a href={useBaseUrl('/labs/lucene-search/SearchLab.java')} download>Complete SearchLab.java</a>

Place them in this structure in a scratch directory outside the learning-site project:

```text
lucene-search-lab/
  pom.xml
  src/main/java/SearchLab.java
```

From `lucene-search-lab`, run:

```bash
mvn compile exec:java -Dexec.args='lexical'
```

The first invocation downloads dependencies from Maven Central. All Lucene modules
are pinned to **10.3.1**. The lab creates five articles, opens a reader, queries
`bicycle repair`, prints hits and scoring explanations, then closes its resources.
Expect public articles A and E. Private article C must not appear. A and E have
the same relevant term counts and lengths, so do not rely on a semantic distinction
between their tied scores.

This program uses `ByteBuffersDirectory`: every run creates a fresh in-memory
index. It deliberately does not demonstrate persistence, a web server, or real
embeddings. The vector and hybrid modes introduced later use hand-assigned vectors.

## A field is a set of capabilities

The lab constructs documents with `StringField` for a stable ID and access label,
`TextField` for prose, and `KnnFloatVectorField` for vector retrieval. A document is
a collection of named fields, not an object whose Java properties automatically
become searchable.

| Need | Typical representation | What it does not imply |
| --- | --- | --- |
| Exact article ID or tenant | `StringField` | No tokenization or automatic normalization |
| Searchable prose | `TextField` | Not sortable by default |
| Display original content | `Store.YES` or `StoredField` | Storage alone does not create search terms |
| Numeric range | `IntPoint`, `LongPoint`, or similar | Not automatically stored or sortable |
| Sort or aggregate a number | `NumericDocValuesField` | Not the same as a point index |
| Vector neighbors | `KnnFloatVectorField` | Does not generate an embedding |

Often one logical property needs several physical fields with the same name.
For a publication year you might add an `IntPoint` for range filtering, a
`NumericDocValuesField` for sorting, and a `StoredField` for display. They support
different access patterns; none is a universal substitute for the others.

## Follow the resource lifetime

Read the `try` blocks in the downloaded lab from outside inward. The analyzer
defines text processing. The directory owns storage. The writer consumes
documents and creates index structures. `DirectoryReader.open(writer)` opens
a near-real-time view of the writer's changes; an `IndexSearcher` uses that view.

```java
try (var reader = DirectoryReader.open(writer)) {
    var searcher = new IndexSearcher(reader);
    var query = new TermQuery(new Term("body", "bicycle"));
    for (var hit : searcher.search(query, 10).scoreDocs) {
        var stored = searcher.storedFields().document(hit.doc);
        System.out.println(stored.get("id"));
    }
}
```

This fragment belongs inside the existing writer scope. Java's try-with-resources
closes the reader even if a query fails. The searcher itself does not require
closing. In a service, reuse a writer and managed searchers; opening everything
for every HTTP request would add unnecessary work and complicate consistency.

## Try it yourself 🧪

In `document(...)`, change only the body's `Field.Store.YES` to `Field.Store.NO`.
Run the lexical command again. The hit IDs should remain A and E, but displayed
bodies become `null`. Restore the setting, then change the body to a `StringField`.
The same query should now return no hits. Restore `TextField` before continuing.

This is a useful debugging sequence: first ask whether the document matches,
then whether the requested display data exists. A missing snippet and a missing
candidate require different fixes. Keep the access filter intact in every experiment.

<details>
<summary>🤓 Durability is a separate decision (optional)</summary>

`FSDirectory.open(Path.of("index"))` uses filesystem storage, but changing the
directory alone is not a complete persistence design. Decide when to commit,
how to reopen, and how to avoid duplicating ingestion on restart. `addDocument`
does not enforce uniqueness of an ID field. An update by stable ID requires
`updateDocument(new Term("id", id), replacement)` and a schema that indexes
that ID exactly. A commit creates a durable index commit; refreshing a reader
changes search visibility. Later lessons separate these operations explicitly.

</details>

## Recap 🐾

1. Indexed, stored, point, and doc-values representations serve different access patterns.
2. A writer changes the index; a reader exposes a view; a searcher executes queries.
3. The downloadable lab resets on each run, so its output is reproducible without cleanup.
