# 8.3 — Encoder-only, decoder-only, encoder–decoder ⏱️ ~10 min · folds are optional extra

## The hook

BERT, GPT, and Whisper are all "transformers". They are built from the same blocks you assembled in lesson 6.1. Yet BERT cannot write you a sentence, GPT cannot look ahead at its own output, and Whisper needs both behaviors at once.

The difference is not exotic. It is a boolean matrix: **who is allowed to attend to whom**.

## The mask is the architecture 🎮

Flip between the three shapes and read the grid. A 👀 cell means "this row's query may read this column's token"; an ✕ means the attention score is set to $-\infty$ before the softmax, so the weight becomes exactly zero:

<AttentionMaskViz />

**Things to try:**

1. On **encoder-only**, find the row for *"the"* and notice it reads *"router"*, four words to its right. That is how the model knows which "the" it is.
2. On **decoder-only**, count the allowed cells per row: 1, 2, 3, 4, 5. Every row is a separate training example for "predict the next token", all in one forward pass.
3. On **cross-attention**, note the grid is no longer square — rows are target tokens, columns are source tokens, and nothing is blocked.

Same blocks, same math, three behaviors. When a paper says "we used a decoder-only architecture", it is mostly telling you about that triangle.

## Encoder-only: understanding, not writing

**Examples:** BERT, RoBERTa, DeBERTa, and the embedding and reranking models you meet in retrieval systems.

Training uses **masked language modeling**: hide about 15% of the tokens and predict them from both sides. Because nothing is causally masked, every token's final vector is informed by the full sentence — ideal for judging, tagging, or embedding text.

What you get out is **vectors, not text**: a sentence embedding for search, a class for sentiment, a span for named entities, a relevance score for a query–document pair. What you do not get is generation. There is no autoregressive loop and no `<eos>` to emit; asking BERT to write a paragraph is asking a lock to be a key.

The efficiency footnote matters at scale: MLM supervises only the masked fraction of tokens per example, while causal LM supervises every position. That difference in learning signal per token is part of why the industry's giant-model money flowed elsewhere.

## Decoder-only: one stack, one objective

**Examples:** GPT, Llama, Mistral, Qwen — nearly every model you call an "LLM".

One causal stack, one objective: predict the next token. The prompt is not a separate input to a separate tower; it is simply a prefix that the model conditions on. "Translate to French: the cat sat" and its answer live in the **same sequence**, which is exactly why instruction following, few-shot prompting, chat, and code completion are all the same machinery wearing different hats.

Practical consequences:

- **KV caching** works beautifully: past tokens' keys and values never change, so generating token 500 reuses 499 cached entries and only computes one new column.
- **No architectural decision** about where "input" ends and "output" begins — a real advantage when your tasks are open-ended.
- **The prefix is causally masked**, so early prompt tokens cannot see later ones. For understanding-heavy inputs that is a genuine handicap compared with a bidirectional encoder; scale and pretraining data have mostly papered over it.

## Encoder–decoder: when input and output are different animals

**Examples:** T5 and BART (text-to-text), Whisper (audio → text), Marian and NLLB (translation).

Use this shape when the source is a fixed, fully available object that deserves bidirectional reading, and the target is a new sequence — often in another language, script, or modality. Whisper is the cleanest case: the encoder consumes a spectrogram (Module 7's world) and the decoder emits text tokens. Making one causal stack chew on audio frames and text in a single sequence would be possible, but you would throw away the encoder's freedom to read the whole clip at once.

The honest comparison:

| | Encoder-only | Decoder-only | Encoder–decoder |
|---|---|---|---|
| Reads input | bidirectionally | causally, as a prefix | bidirectionally |
| Writes output | no | yes | yes |
| Typical use | embeddings, classification, reranking | chat, code, general LLMs | translation, ASR, summarization |
| Extra cost | cheapest | one stack | two stacks + cross-attention |
| Extra benefit | full-context vectors | one objective, in-context learning | source stays fully visible while writing |

Encoder–decoders remain the default in speech and machine translation, where inputs are bounded, outputs are short, latency budgets are tight, and the task is fixed. Decoder-only dominates general-purpose assistants, where the task is whatever the user just typed.

## Tiny example: ask the config

```python
from transformers import AutoConfig

for name in ["bert-base-uncased", "gpt2", "t5-small", "openai/whisper-tiny"]:
    config = AutoConfig.from_pretrained(name)
    print(f"{name:22} encoder_decoder={config.is_encoder_decoder}  {config.architectures}")
```

```text
bert-base-uncased      encoder_decoder=False  ['BertForMaskedLM']
gpt2                   encoder_decoder=False  ['GPT2LMHeadModel']
t5-small               encoder_decoder=True   ['T5ForConditionalGeneration']
openai/whisper-tiny    encoder_decoder=True   ['WhisperForConditionalGeneration']
```

Read the head names, not the hype: `ForMaskedLM` fills blanks, `LMHeadModel` continues text, `ForConditionalGeneration` writes a target sequence given a source. The suffix tells you the shape and the training objective in one word.

<details>
<summary>🤓 The blurry middle (optional)</summary>

The three shapes are a teaching taxonomy, not a law:

- **Prefix-LM** (used by UL2 and some T5 variants) applies bidirectional attention over the prompt and causal attention over the continuation — one stack with two mask regions, sitting between decoder-only and encoder–decoder.
- **Encoder–decoder models can be assembled from two pretrained decoders** (`EncoderDecoderModel` in Transformers), with freshly initialized cross-attention layers.
- **Decoder-only models can do embeddings** by pooling final hidden states, though bidirectional encoders still tend to win per parameter on retrieval benchmarks.

So the useful question is never "which family is best?" It is "what must be visible to what, and when?" The mask follows from the answer.

</details>

## Try it yourself

Assign a shape to each task and justify it in one sentence: (a) flagging support tickets as urgent, (b) live speech transcription with a 300 ms budget, (c) a coding assistant in your editor, (d) semantic search over 2 million documents, (e) translating a product catalog into 12 languages. Then find the one that is genuinely arguable — at least one of these is defensible in two shapes, and the tiebreaker is latency or cost rather than accuracy.

## Recap 📌

- Encoder-only reads bidirectionally and outputs vectors; decoder-only reads causally and writes text; encoder–decoder does both and bridges them with cross-attention
- The attention mask *is* the architectural difference: which queries may read which keys, enforced by setting blocked scores to $-\infty$
- Choose by the job — bounded input plus new-sequence output favors encoder–decoder; open-ended tasks favor decoder-only; scoring and search favor encoder-only
