## Separate the memory budgets

`shared_buffers` holds a shared cache of PostgreSQL data pages. Backends locate
a page, pin its buffer while using it, and take appropriate short-term locks
to inspect or change contents. Pins prevent unsafe reuse; they do not replace
SQL row locks. The operating system also caches file data, so a shared-buffer
miss does not prove a physical device read.

`work_mem` is a base budget for eligible executor operations such as sorts and
hashing, not a single allocation per server or connection. A complex plan can
have several such operations. Multiple queries and parallel workers can multiply
their use. Hash operations can use a budget scaled by `hash_mem_multiplier`.
Actual lifetime, sharing, and allocation vary by node, so this is a planning
bound, not an exact multiplication formula for every plan.

`maintenance_work_mem` serves maintenance commands such as index creation and
manual vacuum. Autovacuum has additional configuration considerations, including
`autovacuum_work_mem`. `effective_cache_size`, by contrast, is a planner estimate
of cache likely available to a query; it does **not** allocate a cache. Increasing
it cannot create RAM, though it can change cost comparisons.

## Observe a spill without changing global settings

Run in the disposable lab:

```sql
BEGIN;
SET LOCAL work_mem = '64kB';
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, customer_id, created_at
FROM course_lab.orders
ORDER BY md5(id::text), id;
ROLLBACK;
```

This intentionally artificial sort has no matching index. Look for Sort Method
and disk or memory usage. At a small budget it should spill on the seeded
20,000-row dataset, but record the actual plan rather than asserting a specific
byte count. Repeat with a larger local budget and compare temp reads/writes,
elapsed time, and sort method. EXPLAIN ANALYZE executes the query.

Spilling is a safety mechanism, not automatically a failure. Making all spills
impossible by raising a global budget can be less reliable than accepting bounded
temporary I/O. Conversely, repeated large spills on a hot path can justify better
indexes, fewer intermediate rows, a rewritten query, or a scoped memory setting.

## Private memory has ownership and lifetime

PostgreSQL organizes much private allocation into **memory contexts**. A context
owns allocations so a query or transaction can release related memory together
rather than individually tracking every object. This helps cleanup on errors,
but does not mean any value can be safely retained after its context is reset.
Extension authors must choose lifetimes carefully.

In your own backend, inspect `pg_backend_memory_contexts` where permitted.
The result describes backend allocations, not total cluster resident memory or
the operating-system page cache. Measure the level relevant to the question.

## Try it yourself 🧪

Compare the two sort budgets, then run the query a second time at each budget.
Separate cache warming from the memory change. Estimate a conservative exposure
for 20 concurrent queries, each with two 16 MB sorts: 640 MB before considering
hash multipliers, shared buffers, private overhead, or other work. Explain why
this is neither a precise resident-memory forecast nor permission to run without
a concurrency limit.

<summary>🤓 Buffer replacement is not a query-result cache (optional)</summary>

The buffer manager tracks page identity, references, dirty state, and usage to
support replacement. Reusing a cached page still requires execution, filtering,
and visibility checks. Start at
[`bufmgr.c`](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/storage/buffer/bufmgr.c)
and `src/backend/utils/mmgr/`. An EXPLAIN buffer hit records a page access
satisfied from shared buffers, not a complete cached answer to the SQL statement.

</details>

## Recap 🐾

1. Shared buffers, OS cache, and private executor memory have different roles.
2. work_mem can multiply across operations and concurrency; effective_cache_size allocates nothing.
3. Measure spills and cache state before changing scoped budgets or global limits.
