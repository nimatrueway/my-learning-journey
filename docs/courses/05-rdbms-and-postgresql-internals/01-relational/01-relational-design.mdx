A product's current price changes. Should every historical order change too?
The answer depends on which fact each column represents, not how efficiently
you can run an UPDATE.

⏱️ **Reading + practice: ~10 min** · includes five minutes of schema experiments.

## Start with facts and dependencies

An RDBMS stores structured data and supports relational operations, constraints,
transactions, and concurrent access. A mathematical relation is an unordered set
of tuples over named attributes. SQL tables are a practical implementation with
important differences: duplicates can exist without a key, NULL represents
missing or unknown information, and query output has no guaranteed order without
ORDER BY. A table's physical page order is not part of your application contract.

A **candidate key** uniquely identifies a row with no unnecessary attributes.
A primary key is the candidate key chosen as the main identifier. In the
[lab schema](../labs.mdx), `products.id` identifies a product and
`(order_id, product_id)` identifies one product's line within an order. That
composite key deliberately disallows two separate lines for the same product
in one order. A business that needs separate customizations would choose a
different line identity. A key is a business decision, not just an index knob.

Normalization follows dependencies. If product ID determines the current name
and current price, repeat those attributes in every order and you create update
anomalies: one correction needs many writes, and partial corrections disagree.
Separate products from orders and join when needed. But `order_items.unit_price`
means **the price agreed for that sale**, which can differ from today's catalog
price. Keeping it is not accidental duplication of the same fact.

## Put enforceable invariants in the database

Inspect the setup file. `NOT NULL` rejects absence, `CHECK (stock >= 0)` rejects
negative inventory, and foreign keys reject references to missing products.
The database enforces these rules regardless of which application or maintenance
script writes the data. An application-only "does this key exist?" query races
with another writer. A unique constraint arbitrates concurrent inserts.

PostgreSQL CHECK accepts true **or unknown**, so `CHECK (price >= 0)` alone does
not reject NULL. Pair it with NOT NULL when absence is invalid. A foreign key
column can also be nullable; in this fixture the composite primary key makes
both reference columns non-null. The referenced key is indexed, but PostgreSQL
does not automatically create an index on every referencing foreign-key column.
The line-item primary key begins with `order_id`; product-oriented access may
need a separate index after measurement.

## Test the boundary, not just the happy path

Run each statement separately in psql, outside an explicit transaction:

```sql
UPDATE course_lab.products SET stock = -1 WHERE id = 1;
UPDATE course_lab.products SET price = NULL WHERE id = 1;
INSERT INTO course_lab.products VALUES (1, 'Other', 2.00, 3);
SELECT id, name, price, stock FROM course_lab.products ORDER BY id;
```

The first three statements fail on CHECK, NOT NULL, and primary-key uniqueness
respectively. The final query still returns the original valid rows. In an
explicit transaction, the first error instead leaves the transaction aborted
until ROLLBACK, unless you recover through a previously created savepoint.
This distinction matters when turning a psql experiment into application code.

## Try it yourself 🧪

Write a tiny dependency list for customers, orders, and line items. Identify
which address means "current customer address" and which means "shipping
address chosen for this order." Explain whether historical address snapshots
are intended. Then try inserting a line item for a nonexistent order and predict
the foreign-key error. Finally decide whether the invariant "at least one
operator is on call" fits a row CHECK. It spans rows; a CHECK that queries
other rows is not the right concurrency-safe enforcement mechanism.

<details>
<summary>🤓 Normal forms without ritual (optional)</summary>

Third normal form aims to keep non-key attributes dependent on keys without
problematic transitive dependencies. Boyce-Codd normal form requires every
determinant of a nontrivial functional dependency to be a superkey. Decomposition
should preserve information through a lossless join; some decompositions make
dependencies harder to enforce locally. Start with explicit dependencies and
workload needs, not a universal command to split every column into a table.
Intentional denormalization needs an owner, refresh policy, and repair strategy.

</details>

## Recap 🐾

1. Keys and dependencies describe the identity and meaning of facts.
2. Constraints protect all write paths, but each constraint has precise NULL and concurrency semantics.
3. Historical snapshots and intentional denormalization need explicit meaning and maintenance rules.
