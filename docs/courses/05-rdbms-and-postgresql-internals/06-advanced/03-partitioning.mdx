## Partition bounds select relations

Declarative partitioning routes rows from a partitioned parent into child
partitions using range, list, or hash bounds. The parent is a logical entry
point; the child relations store rows. Partition pruning uses compatible query
conditions to exclude children that cannot contribute, at planning or execution
time depending on available values and plan shape. Indexes solve a separate
problem: efficiently locating rows within the chosen partitions.

Range lower bounds are inclusive and upper bounds exclusive. A row with no
matching partition fails unless a suitable default partition exists. A default
partition can catch unexpected rows but introduces lifecycle work when attaching
new explicit ranges. Define timezone and boundary semantics deliberately for
timestamp partition keys.

```sql
BEGIN;
CREATE TABLE course_lab.event_probe (
  event_date date NOT NULL,
  id bigint NOT NULL,
  PRIMARY KEY (event_date, id)
) PARTITION BY RANGE (event_date);
CREATE TABLE course_lab.event_probe_jan PARTITION OF course_lab.event_probe
  FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
CREATE TABLE course_lab.event_probe_feb PARTITION OF course_lab.event_probe
  FOR VALUES FROM ('2025-02-01') TO ('2025-03-01');
INSERT INTO course_lab.event_probe VALUES
  ('2025-01-12', 1), ('2025-02-12', 2);
EXPLAIN (ANALYZE, COSTS OFF)
SELECT * FROM course_lab.event_probe
WHERE event_date >= DATE '2025-02-01'
  AND event_date < DATE '2025-03-01';
SELECT tableoid::regclass, * FROM course_lab.event_probe ORDER BY event_date;
ROLLBACK;
```

Expect the filtered plan to access only the February partition with one row.
The exact access node may differ; scanning a tiny child is reasonable. The
tableoid projection reveals the physical child containing each row. Rollback
removes this whole bounded fixture so the example can be repeated.

## Keys and lifecycle shape the design

In PostgreSQL 17, a PRIMARY KEY or UNIQUE constraint on a partitioned table must
include all partition-key columns, with restrictions on partition expressions.
Local child indexes alone cannot enforce arbitrary global uniqueness across
partitions. The example allows the same id on different dates; including the date
in the key is a real semantic decision, not a syntax workaround that preserves
global id uniqueness.

Detaching or dropping an old partition can make time-based retention more
manageable than deleting millions of rows individually. Lock requirements,
foreign keys, concurrent operations, backups, and application expectations still
matter. Partition attachment may validate bounds by scanning existing data unless
appropriate constraints prove compatibility. A fast-looking DDL command needs a
lock and rollback plan before production use.

Too many partitions increase planning, metadata, memory, and management overhead.
Queries lacking useful partition-key conditions may touch many children. Updating
a partition key can move a row to another partition and has concurrency
implications. Partitioning is neither sharding across servers nor an automatic
replacement for indexes, vacuum, statistics, or sensible query design.

## Try it yourself 🧪

Run the fixture and identify the pruned child. Repeat with only `WHERE id = 2`
and compare the accessed children. Before rollback, try an additional row with
the same id on a different date: explain why the composite primary key permits
it. Then predict where March 1 would route with the current bounds. Separate
the routing error from uniqueness enforcement in your explanation.

<details>
<summary>🤓 Pruning is not constraint exclusion (optional)</summary>

Declarative partition pruning understands partition bounds directly. The older
constraint-exclusion mechanism reasons from constraints and has different timing
and capabilities. Prepared parameters can make execution-time pruning relevant;
EXPLAIN evidence such as removed subplans or never-executed children needs to be
interpreted with that plan. See `src/backend/partitioning/partprune.c` for the
version-specific implementation.

</details>

## Recap 🐾

1. Partition pruning excludes irrelevant child relations; indexes locate rows inside selected children.
2. Partition keys constrain uniqueness, routing, and data-lifecycle operations.
3. Partitioning should match measured access and retention patterns, not serve as a universal speed switch.
