## Metadata lives in relations too

The pg_catalog schema contains PostgreSQL's system catalogs. `pg_class` describes
relations, including tables, indexes, sequences, and other relation kinds.
`pg_namespace` identifies schemas; `pg_attribute` describes columns; `pg_type`
describes types. `pg_constraint` stores constraint metadata, while `pg_index`
describes index properties and validity. A relation's object identifier, or OID,
is an internal identity within this database, not a durable business identifier
to move between independent environments.

Catalogs participate in database machinery and expose version-specific details.
Use supported DDL to change objects, not direct UPDATE statements against system
catalogs. Editing an internal row bypasses invariants and dependency handling.
The information_schema offers more portable standardized views, though it does
not expose every PostgreSQL-specific feature and visibility depends on privileges.

```sql
SELECT namespace.nspname, relation.relname, relation.relkind
FROM pg_class AS relation
JOIN pg_namespace AS namespace ON namespace.oid = relation.relnamespace
WHERE namespace.nspname = 'course_lab'
ORDER BY relation.relname;

SELECT conname, contype, convalidated, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'course_lab.products'::regclass
ORDER BY conname;

SELECT attname, format_type(atttypid, atttypmod), attnotnull
FROM pg_attribute
WHERE attrelid = 'course_lab.products'::regclass
  AND attnum > 0 AND NOT attisdropped
ORDER BY attnum;
```

The regclass cast resolves a relation name to its OID. Schema qualification
avoids accidentally selecting a same-named relation elsewhere on search_path.
`pg_get_constraintdef` and `format_type` provide readable representations instead
of making the learner decode every internal field. In PostgreSQL 17, inspect
attnotnull for a column's NOT NULL property rather than assuming every such
property is represented like a CHECK row in pg_constraint.

## Definitions, measurements, and plans are different evidence

Catalog definitions answer what exists. Cumulative statistics views answer what
has been observed, subject to resets, update timing, estimates, and visibility.
Planner statistics summarize data distributions, and an execution plan describes
a particular chosen strategy. None is a substitute for all the others.

An index can exist but be invalid or not ready after an interrupted concurrent
build. A valid index still might not be selected for a particular query. A
low usage count could reflect a recent reset rather than permanent uselessness.
Dropping an index also affects constraint enforcement and write/read tradeoffs,
so an isolated counter is not a sufficient deletion policy.

pg_depend records relationships used to maintain object dependencies. A view
depending on a table or an extension owning objects changes what can be dropped
independently. RESTRICT and CASCADE express consequential behavior, not merely
syntax preferences. Start source inspection at
[`dependency.c`](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/catalog/dependency.c)
and catalog definitions in `src/include/catalog/`. Read before experimenting
with destructive dependency changes.

## Recap 🐾

1. System catalogs describe installed objects; supported DDL preserves their invariants.
2. Schema-qualified regclass and readable definition functions make metadata inspection safer and clearer.
3. Definitions, statistics, and actual execution plans answer different diagnostic questions.
