## A. Identify transactions without inventing timestamps

Every transaction has a virtual transaction identifier. PostgreSQL assigns a
normal XID lazily when it needs one, usually on its first database write.
A read-only transaction may never receive one. `pg_current_xact_id()` explicitly
forces allocation; `pg_current_xact_id_if_assigned()` does not. XIDs are allocated
from a cluster-wide counter, not separately for each table or database.

The tuple-header `xmin` is the inserting transaction's XID, **not creation time**.
For an ordinary delete or update, `xmax` identifies the deleting/updating
transaction, **not removal time**. Additional flags determine what these fields
mean. A nonzero `xmax` can be a lock-only marker or a MultiXact ID describing
multiple lockers and possibly an updater. An aborted deleter does not make the
row invisible. Never implement visibility using these two columns alone.

Normal on-page XIDs are 32-bit and wrap. Full `xid8` values include an epoch;
they are suitable for the SQL snapshot functions. Numeric examples here stay
within one epoch. Production code uses wraparound-aware comparisons and freezing,
not ordinary unbounded integer ordering over raw tuple XIDs.

## B. Capture a snapshot, not a moving pending list

Distinguish **tuple** xmin/xmax from **snapshot** xmin/xmax. The names overlap
but the meanings do not. A snapshot records boundaries and a captured set of
transactions in progress. The SQL representation is `xmin:xmax:xip_list`.

For the teaching snapshot `100:105:100,103`:

| XID | Snapshot interpretation |
| --- | --- |
| Below 100 | Completed before the snapshot, but might have aborted |
| 100 or 103 | Was in progress at capture; invisible as an external creator |
| 101, 102, 104 | Completed before capture; check whether it committed |
| 105 or greater | Not completed by capture; invisible to this snapshot |

The upper boundary is exclusive. It is not the reader's XID, nor necessarily
"the next XID someone will allocate." A Repeatable Read reader retains the
captured set even after transaction 100 commits. Removing 100 from a live global
pending set must not retroactively change the old snapshot. Read Committed gets
a new snapshot at the next statement instead.

For **ordinary versions written by other top-level transactions**, ignoring
wraparound, subtransactions, freezing, and lock-only/MultiXact states, reason as:

```text
committed_before_snapshot(xid) =
  transaction_status(xid) is committed
  AND xid < snapshot.xmax
  AND xid is not in snapshot.xip

visible(version) =
  committed_before_snapshot(version.xmin)
  AND NOT committed_before_snapshot(version.deleting_xid)
```

An absent or invalid deleting XID does not count as a committed deletion.
This is a deliberately restricted mental model, **not PostgreSQL's complete
visibility function**. A creator that aborted is never visible even though it
is absent from the active set. A deleter that aborted leaves the older version
visible when its creator is visible. A deleter still running at capture cannot
hide that version from the retained snapshot.

Own writes need a separate branch: previous statements in the same transaction
can see its own inserts and stop seeing its own deletes. Command IDs distinguish
changes made before a statement from those made during it. Subtransactions,
hint bits, frozen tuples, and MultiXacts require further logic. "Exclude myself
from pending" is not enough to reproduce all these cases.

## C. Follow the version chain

For a simple heap tuple inserted by XID 90, updated by 101, then deleted by 108:

```text
INSERT 90:  v1(value=10, xmin=90,  xmax=invalid)
UPDATE 101: v1(value=10, xmin=90,  xmax=101)
            v2(value=9,  xmin=101, xmax=invalid)
DELETE 108: v2(value=9,  xmin=101, xmax=108)
```

UPDATE creates a new version and marks the predecessor; DELETE does not instantly
erase bytes. The old tuple's `t_ctid` can link to the successor. Commit status
and the reader's snapshot determine which version is visible. If 101 aborts,
its new version stays invisible and v1 is still eligible. The engine protects
these transitions with locks and internal synchronization; two writers do not
blindly race to store different xmax values.

## Try it yourself 🧪

In a fresh psql connection, compare lazy and forced XID allocation:

```sql
BEGIN;
SELECT pg_current_xact_id_if_assigned();
SELECT pg_current_xact_id();
SELECT pg_current_xact_id_if_assigned();
SELECT pg_current_snapshot();
ROLLBACK;
SELECT pg_snapshot_xmin('100:105:100,103'::pg_snapshot),
       pg_snapshot_xmax('100:105:100,103'::pg_snapshot);
SELECT * FROM pg_snapshot_xip('100:105:100,103'::pg_snapshot);
```

Expect NULL before forcing allocation, then the same assigned XID twice. The
synthetic snapshot exposes boundaries 100 and 105 and active entries 100 and
103. Use the widget to classify a committed and an aborted creator with XID
102: the numeric boundaries are identical, yet the answers differ.
`pg_visible_in_snapshot()` tests snapshot completion membership for top-level
XIDs; it is not a standalone proof that a heap tuple's creator committed.

## Recap 🐾

1. XIDs identify transactions, not timestamps, and normal XIDs are allocated lazily and wrap.
2. Snapshot boundaries, captured active transactions, commit status, and tuple flags jointly control visibility.
3. INSERT, UPDATE, and DELETE change version metadata; own commands, locks, and subtransactions add essential cases.
