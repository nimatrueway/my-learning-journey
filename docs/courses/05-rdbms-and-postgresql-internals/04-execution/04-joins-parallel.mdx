## Three join mechanisms

A **nested loop** takes an outer row and obtains matching inner rows repeatedly.
It is excellent for a small outer input with an efficient parameterized index
lookup, and can produce early output. It becomes costly when underestimated
outer cardinality multiplies a large inner scan. Materialize or Memoize nodes
can change the repeated-work story; inspect the actual child plan.

A **hash join** builds a hash table from one input and probes it with the other
for supported equality conditions. The build is startup work. If the working
set exceeds its memory budget, batching and temporary files can appear. A hash
join is not a general solution for every non-equality predicate, nor is hashing
automatically faster than using an already suitable index.

A **merge join** advances through inputs ordered compatibly with mergeable join
conditions. Those orders can come from indexes or explicit sorts. Duplicate
keys require correct matching of groups rather than simply zipping rows one
for one. Sorting both large inputs may dominate the benefit if no order already
exists. Join order and join algorithm interact: the output size of an earlier
join changes the cost of every later stage.

## Compare a real plan with counterfactuals

This intentionally pairs orders from the same customer; it is not a revenue query:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*)
FROM course_lab.orders AS first_order
JOIN course_lab.orders AS other_order
  ON first_order.customer_id = other_order.customer_id
WHERE first_order.id <= 1000;
```

With the untouched seed, the result is 20,000 pairs: 1,000 outer orders each
match 20 orders for their customer, including themselves. Verify this grain
before discussing performance. The planner can choose different paths depending
on indexes from earlier lessons.

For a local diagnostic comparison, wrap the query in BEGIN, use SET LOCAL
enable_hashjoin = off, inspect the alternative, and ROLLBACK. Planner switches
are investigative tools, not proof that the alternative is universally better.
Always compare actual rows, loops, buffers, temporary I/O, and time under a
representative workload before preserving a setting.

## Parallel plans divide only eligible work

A parallel plan introduces worker participation, often through Gather or Gather
Merge. Gather collects worker output without preserving a global sort order;
Gather Merge merges appropriately ordered streams. A leader can participate
in execution as well as consume results. Workers planned and workers launched
can differ because of runtime availability and limits.

Parallel-aware scans divide work rather than making every worker scan every row.
Some plan components can still duplicate work or require serial coordination.
Partial aggregation in workers followed by final aggregation reduces transfer
when the aggregate supports it. Parallel Hash has a shared-hash implementation;
not every hash join under Gather has the same memory-sharing behavior.

```sql
SHOW max_parallel_workers_per_gather;
EXPLAIN SELECT sum(customer_id) FROM course_lab.orders;
```

The 20,000-row fixture may correctly choose a serial plan. Startup, communication,
worker availability, function safety, and estimated savings all matter. Do not
inflate a production table or change global thresholds simply to display Gather.

## Try it yourself 🧪

Run the pair-count query with outer ID limits 5 and 1,000. Explain any plan
change using input cardinality and the existing customer index. Inspect loops
on inner nodes. Then use plain EXPLAIN on the aggregate and record whether a
parallel path was chosen. Name the evidence that would justify parallelism on
a larger workload without assuming worker count equals speedup.

## Recap 🐾

1. Join algorithms trade startup, ordering, memory, and repeated work differently.
2. Join cardinality and available access paths determine which tradeoff is useful.
3. Parallelism requires eligible divisible work and enough savings to repay coordination costs.
