# How to Build an MVP in the AI Coding Era

AI can turn a feature request into code before the founder has decided whether
the feature should exist. The bottleneck did not vanish. It moved from typing
software toward choosing what deserves to be learned.

⏱️ **~8 min** · ~1,200 words at 200 wpm + 2 minutes of practice · the 12-minute source video is optional

Dalton Caldwell and Michael Seibel revisit classic minimum-viable-product advice
under cheaper implementation. They do not settle on “more features” or “fewer
features” as a universal answer. Their durable test is whether the product helps
customers become more successful. The source explicitly treats the net effect
of cheaper feature production as unclear.

## Minimum Refers to Learning, Not Code Volume

Historically, implementation cost forced teams to choose a narrow feature set.
AI coding tools loosen that constraint, but they do not make attention,
integration, reliability, support, or user comprehension free.

Define an MVP by a learning loop:

1. **Person:** A specific user with a costly situation.
2. **Outcome:** One observable improvement they care about.
3. **Experience:** The smallest coherent path that can produce that outcome.
4. **Signal:** Behavior or evidence that would support or reject the thesis.
5. **Deadline:** A short date when the team will inspect the evidence.

AI may allow a richer first experience when polish or integration is necessary
to test the outcome. It may also create a broad product that obscures which
capability produced value. “We can build it tonight” answers a production
question, not a product question.

## Source Case: Most Built Features Did Not Matter

One host describes recently building and launching a product with AI assistance,
then estimating that roughly 80 percent of the MVP's features were unnecessary.
The precise percentage is a personal retrospective, not measured evidence.
Its value is the mechanism: feature creep once consumed months, which imposed a
natural stopping cost; now an agent can make speculative additions feel almost
free.

The hidden cost appears later. Every feature expands the surface to explain,
test, debug, secure, and interpret. Worse, a founder building for someone else
can imagine an infinite list of things “they would want.” A founder building
for their own workflow at least has direct use as one signal, though a sample of
one still cannot establish a market.

## Let User Pull, Not Tool Push, Expand the Product

Dalton's heuristic is to resist broad, complex products and add capability when
users pull the team toward it, not merely because Codex can produce it. User
requests are inputs, not commands: customers understand their desired success
better than they necessarily understand the product design that will create it.

Before adding a requested feature, ask:

- What failed in the user's current workflow?
- What outcome are they trying to obtain?
- Can the existing product or a manual service test that outcome first?
- What behavior after shipping would show that the addition mattered?
- What will we remove or stop maintaining if the signal does not appear?

This keeps cheap implementation attached to expensive learning.

## Automation Can Produce Fake Customer Contact

The source extends the same warning to distribution. AI makes it easy to buy
leads and send enormous volumes of outreach. Big activity numbers can disguise
the absence of listening. The hosts prefer a smaller number of high-quality
conversations over spamming a thousand people.

That is a heuristic, not a ban on automation. Automation is useful after the
team knows whom it serves, what respectful message is relevant, and how replies
feed product decisions. It is weak as a substitute for discovering those facts.

## Try It Yourself: Run a 30-Minute Feature Trial

Pick one planned feature. Spend 10 minutes writing the user, desired outcome,
and observable success signal. Spend 10 minutes designing the cheapest manual,
prototype, or AI-built test. Spend the final 10 minutes naming a removal rule:
if the signal does not appear after a fixed number of uses or by a fixed date,
the feature leaves the MVP.

The boundary is one feature, one user type, one signal, and one week. Do not let
the coding agent turn the trial into a platform rewrite.

## Cheap Code Changes the Caveats Too

Generated code can be fast while remaining insecure, inaccessible, unreliable,
or difficult to maintain. High-risk domains require stronger review regardless
of prototype speed. Some products also need multiple integrated features before
a user can experience any value; artificial minimalism can invalidate the test.

The right scope depends on the outcome being tested. The discipline is not
minimal feature count. It is minimal unsupported assumption.

<details>
<summary>🧪 An AI-generated feature gate (optional)</summary>

Ship a generated feature only when the team can answer:

- **Reason:** Which observed user problem justifies it?
- **Owner:** Who understands and maintains the resulting code?
- **Review:** What security, privacy, quality, and accessibility checks apply?
- **Signal:** Which behavior will show that it creates value?
- **Exit:** When will it be removed if the signal stays absent?

Prototype code may receive lighter engineering investment, but user risk should
determine review depth. “The model wrote it” transfers neither accountability
nor maintenance.

</details>

## Three Things to Keep

- AI lowers implementation cost but does not lower the cost of product confusion, maintenance, or user risk.
- Define an MVP around a specific outcome and learning signal rather than the number of features it contains.
- Expand when observed users pull the product toward value, not when a coding tool pushes the team toward easy output.
