## Stable reads are not serial execution

PostgreSQL Repeatable Read provides snapshot isolation and prevents phantoms
from concurrent commits. It can still permit **write skew**. Alice's transaction
reads Bob and writes Alice; Bob's reads Alice and writes Bob. A same-row
write-write conflict does not arise, but the cross-row rule is broken.

Under a serial execution, the second transaction would see only one available
operator and would not sign off. The outcome therefore cannot be explained by
any serial ordering of these correctly implemented decisions. Consistency
requires protecting the read-based decision, not merely the final row update.

## Reproduce the anomaly

Initialize the [lab](../labs.mdx), finish old transactions, and reset both
operators to available. In **both A and B**, run:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM course_lab.on_call WHERE available;
```

Both see 2. A runs:

```sql
UPDATE course_lab.on_call SET available = false WHERE name = 'alice';
COMMIT;
```

B then runs:

```sql
UPDATE course_lab.on_call SET available = false WHERE name = 'bob';
COMMIT;
```

A fresh count returns 0. The application decision was "update only if my
earlier count exceeded one," and that was true in both snapshots.

## Serializable tracks dependencies

Reset and repeat with `BEGIN ISOLATION LEVEL SERIALIZABLE` in both sessions.
PostgreSQL Serializable Snapshot Isolation tracks read/write dependencies and
rejects dangerous executions with SQLSTATE `40001`. At least one transaction
must fail in this conflicting schedule. In a general race, do not depend on a
particular victim or exact failure statement.

The predicate locks shown as SIReadLock track dependencies; they do not block
writers like ordinary row locks. Monitoring adds overhead and can abort
conservatively. All transactions participating in the invariant must follow the
chosen isolation or locking protocol. Serializable cannot fix an application
that unconditionally turns everybody off call.

## Retrying means recomputing

Roll back after a serialization failure, start a new transaction, reread the
state, and recompute the decision. The remaining operator may now be the only
one available, so the correct result is "cannot sign off." Resending only the
old UPDATE defeats the business logic that justified it. Use bounded attempts
and backoff, and keep non-idempotent external effects out of replayable work.

Read Committed has another behavior for same-row writes: after waiting for a
committed updater, it can recheck the WHERE condition on the new version and
apply its operation there. Repeatable Read instead raises `40001` if a targeted
row changed after its snapshot. This internal recheck is not an automatic retry
of all your application code. Both PostgreSQL and InnoDB coordinate conflicting
writers with locks; they differ in subsequent isolation semantics.

## Try it yourself 🧪

Run both on-call schedules and record the failure statement and SQLSTATE.
Retry the failed business decision from BEGIN and explain why it now declines.
Next establish a Repeatable Read snapshot of product 1 in A, update it and commit
in B, then try updating it in A. Expect a concurrent-update serialization failure.
Repeat at Read Committed with `stock = stock - 1` and compare the result. Finish
both sessions and restore stock to 10 and both operators to available.

## Recap 🐾

1. Write skew breaks cross-row rules without dirty reads or same-row overwrites.
2. Serializable detects dangerous dependencies and can abort with SQLSTATE 40001.
3. A retry must reread and recompute the whole decision under a consistent protocol.
