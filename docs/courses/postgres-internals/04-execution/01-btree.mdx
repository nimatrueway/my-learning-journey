## From root to leaf to heap

A B-tree uses ordered keys and branching pages to locate a leaf range. Internal
pages guide descent; leaf entries point toward matching heap tuples. Sibling
links and concurrency protocols allow scans to keep working as pages split.
The exact implementation is a concurrent storage structure, not a static
binary-search tree. High fanout keeps the tree shallow even with many rows.

An index answers an access-path question, not automatically an MVCC visibility
question. Ordinary index scans visit heap versions to check visibility and
retrieve data. An index-only scan needs both returnable indexed values and a
visibility-map indication that the relevant heap page is all-visible; otherwise
it still performs heap fetches. Recent writes clear visibility information.
Vacuum can restore all-visible bits when safe.

## Align equality, ordering, and payload

For the seeded orders, create a covering B-tree:

```sql
CREATE INDEX IF NOT EXISTS orders_customer_recent
ON course_lab.orders (customer_id, created_at DESC, id DESC)
INCLUDE (status);
VACUUM (ANALYZE) course_lab.orders;
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at, status FROM course_lab.orders
WHERE customer_id = 42
ORDER BY created_at DESC, id DESC LIMIT 5;
```

The leading equality narrows the range. The remaining key order can supply the
requested ordering with a deterministic tie-breaker. INCLUDE stores payload
without making status part of the search ordering or uniqueness key. It can
help an index-only scan, but larger leaf entries cost storage and write work.
Do not add every column "just in case."

For PostgreSQL 17 B-trees, leading equalities and the first range condition
most effectively bound a scan. Conditions on later columns may still be checked
in the index without limiting how much of it must be scanned. Avoid turning
"leftmost prefix matters" into "every other index use is impossible." Inspect
the plan and version-specific behavior rather than transferring newer features.

## Partial and expression indexes encode assumptions

A partial index contains only rows satisfying its predicate. An index on pending
orders can be small and useful for queue access, but the planner must be able
to prove the query implies its predicate. A generic parameterized predicate
may not supply that proof. An expression index can support an expression such
as lower(name), but the query's operator, collation, and expression semantics
must match. These are contracts, not universal text-search accelerators.

CREATE INDEX normally blocks concurrent writes during its build. CREATE INDEX
CONCURRENTLY reduces that blocking but takes additional work, cannot run in a
transaction block, and can leave an invalid index after failure. It is not
"free online DDL." Check validity and resource impact before retrying a large
production build; the tiny lab index uses the ordinary form deliberately.

## Try it yourself 🧪

Save the plan before and after creating the index. Compare Sort nodes, heap
fetches, buffers, and estimated versus actual rows. Update one order for customer
42, commit, and rerun: can the index-only path still need heap visibility checks?
Vacuum and inspect again. Do not demand an exact fetch count, since page layout
and other maintenance affect it. Explain why status as INCLUDE is different
from status as the leading key.

## Recap 🐾

1. B-tree order can support lookup and output order, while heap access still supplies visibility when needed.
2. INCLUDE, partial predicates, and expressions optimize specific query contracts at a write/storage cost.
3. Index-only eligibility and zero heap fetches are different claims; verify plans and visibility state.
