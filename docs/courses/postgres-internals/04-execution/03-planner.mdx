## Costs depend on estimated cardinality

ANALYZE samples table data to estimate distributions: NULL fraction, distinct
counts, common values, histograms, and correlation. These estimates, relation
sizes, available indexes, and cost parameters inform path choice. Costs are
relative units, not milliseconds. `random_page_cost` and CPU costs represent
assumptions; changing them to force one query can damage many other plans.

EXPLAIN's startup and total costs distinguish work needed before producing rows
from work to complete the node. LIMIT can favor a low-startup path. Estimated
`rows` describe node output, not always all rows inspected. A filter may inspect
many tuples to emit few, so examine conditions and rows removed as well.

EXPLAIN ANALYZE executes the statement. For modifying SQL it performs the writes;
ROLLBACK can undo transactional changes but not every possible external function
effect or sequence allocation. Use a disposable environment and understand
triggers before treating ANALYZE as harmless inspection.

## Create a known correlation

Run a temporary two-value fixture:

```sql
CREATE TEMP TABLE planner_probe AS
SELECT item,
       CASE WHEN item % 2 = 0 THEN 'west' ELSE 'east' END AS region,
       CASE WHEN item % 2 = 0 THEN 'US' ELSE 'JP' END AS country
FROM generate_series(1, 10000) AS series(item);
ANALYZE planner_probe;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM planner_probe WHERE region = 'west' AND country = 'US';
CREATE STATISTICS planner_probe_joint (mcv, dependencies)
ON region, country FROM planner_probe;
ANALYZE planner_probe;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM planner_probe WHERE region = 'west' AND country = 'US';
```

Half the rows have each value, but the two predicates are perfectly correlated:
the conjunction matches 5,000, not the 2,500 implied by multiplying independent
half-probabilities. Extended statistics can represent this relationship and
improve the estimate. They do not create an access path, and they do not solve
every expression, join, or cross-table estimation problem.

## Read actual metrics without double-counting

Actual rows and times on a repeated node are generally per-loop averages.
Multiply rows by loops to understand repeated output, but do not sum parent and
child elapsed times as independent work: parent timing includes child work.
Parallel plans add worker-specific interpretation. Use the plan tree, not a
spreadsheet that blindly totals every number.

BUFFERS distinguishes hits, reads, dirtied/written buffers, and temporary I/O
when present. A shared read can be served by the OS cache. Total query latency
also includes planning, network transfer, result decoding, and application work
that a server executor plan does not fully measure. Record representative
parameters and comparable cache conditions when comparing plans.

## Try it yourself 🧪

Record estimated and actual rows before and after the joint statistics. Change
the conjunction to west and JP and predict zero rows. Inspect the result without
expecting the planner to always estimate literal zero. Then examine customer
42 and pending orders in the main fixture. Explain the correlation before
deciding whether higher statistics targets, extended statistics, or a different
schema/query is appropriate. Never start by changing every cost constant.

## Recap 🐾

1. Cardinality estimates drive cost choices; inspect the earliest major error first.
2. ANALYZE and extended statistics model distributions but do not create indexes or solve every dependency.
3. Costs, per-loop actual metrics, buffers, and application latency measure different things.
